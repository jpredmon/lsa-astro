# skatelawrence.com Migration — Phase 8: Footer (Support/Donate + Social + Copyright) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the site's final page-chrome piece: a real `<footer>` containing three flush sub-blocks — a "Support our work" donate CTA (heading, two paragraphs, Donate button, tax-receipt email), a social-icons row (Instagram/Facebook), and a copyright line. This is the last unbuilt piece of the 9-phase migration.

**Scope note (combines the spec's Phase 8 "Support/Donate" and Phase 9 "Footer"):** live research (this plan's Key discovery 1) found both spec sections are one single live `<footer>` HTML landmark with zero gap between its three sub-blocks — building them as two separate phases would mean Phase 8 ships a donate CTA with no footer element around it, an artificial and never-actually-live intermediate state. Combined into one phase per user confirmation during this plan's scoping. `lsa-site-migration-spec.md` will get a note on this combination (Task 5), matching the project's established spec-correction convention from prior phases.

**Architecture:** `Footer.astro` — one self-contained component with three internal `<section>`s, mounted in `BaseLayout.astro` (alongside `<Header />`, not inside `index.astro`'s `<main>` — see Key discovery 6). Reuses the existing `DonateButton.astro` with a new third variant. Social icons are inline SVGs (no new icon-library dependency — see Key discovery 5).

**Tech Stack:** Astro components, existing design tokens (h2/body typography and `--space-sm` reused directly — no new spacing tokens needed for this phase).

## Context

Phases 1–7 (scaffold, tokens, header/nav, hero, about, parks, who-we-are) are complete and live at `lsa-astro.pages.dev`. This phase adds the last piece: the footer. Phase 7 left a parked note that `WhoWeAre.astro` expects a flush footer at `margin-top: 0` — confirmed true this phase (Key discovery 1).

**Research method:** live HTML via `curl` with a realistic UA, plus live Chrome `getComputedStyle`/DOM inspection against `https://skatelawrence.com`, at a 1536px viewport.

## Key discovery 1: the whole footer is one flush block — confirms and resolves Phase 7's parked note

Live-measured: `<footer id="main-footer">`'s top edge sits at the exact same y-coordinate as Who We Are's blurb's bottom edge (0px gap, already built correctly in Phase 7). Inside the footer, all three sub-sections are flush against each other too: the Support section's own bottom padding is `0`, the social-icons section's top padding is `0`, and the copyright section's top padding is `0` — no separate spacer/margin between any of the three. `Footer.astro`'s own top-level element needs no top margin at all; Phase 7's parked concern is resolved by this phase simply not adding one.

## Key discovery 2: "Support our work" heading is a PLAIN `<h2>`, not the `AnimatedHeadline` component

Unlike every other section headline built so far (About Us, Our Parks, Who We Are — all `elementor-widget-vamtam-animated-headline`), this heading's live widget type is a plain `elementor-widget-heading` — **no animated underline, no highlight color, no cycling text.** Live-measured: `font-size: 50px`, `line-height: 60px` (i.e. `1.2em`) — **exactly matches the existing `--font-size-h2`/`--line-height-h2` tokens** already in `tokens.css`. Build as a plain `<h2>Support our work</h2>`, centered, no `AnimatedHeadline` import needed.

## Key discovery 3: Donate button needs a new, third `DonateButton` variant

`src/components/header/DonateButton.astro` (built in Phase 3) already has `'desktop'` (transparent bg, 2.4px ink border, hover-inverts) and `'mobile'` (yellow bg, 1px ink border) variants, both using the same `DONATE_URL`. Live-measured on this footer's Donate button: `padding: 18px 55px` (matches `'desktop'`'s padding), `background-color: rgb(238, 211, 56)` (= `--color-highlight-yellow`, matches `'mobile'`'s color), **but `border: 0px none`** (no border at all — matches neither existing variant). This is a genuine third combination: desktop's large padding + mobile's yellow fill + no border. Add a `'cta'` variant to the existing component (extend the `Props` union, add one new CSS rule) rather than creating a new button component — same generalize-an-existing-component pattern as `AnimatedHeadline`'s `cycleDurationMs` prop in Phase 4/5. Hover behavior wasn't captured live; default to the same ink-invert transition already used by `'desktop'`, to be confirmed/adjusted during this phase's own live QA (Task 4).

## Key discovery 4: content is narrower here than every prior section — an intentional, different column width

Every prior section (`About`, `Parks`, `WhoWeAre`) uses `--container-max-width` (1260px) with `--space-sm` (30px) side padding for its text content. This section's text content is measurably narrower: live shows an outer wrapper at 800px width containing 160px of its own left/right padding, netting a **480px** content column, centered — confirmed on the heading, both paragraphs, the button, and the receipt line (all measured at exactly 480px width). Rather than replicate Elementor's two nested padding layers, fold it into one simplified rule: an inner content div with `max-width: 480px; margin: 0 auto;` inside the section (which itself uses the standard `--container-max-width`/`--space-sm` pattern) — same fold-nested-layers-into-one-value approach used throughout this project.

**Note on the apostrophe:** live text is "We've" (curly apostrophe, `’` U+2019) — use the same character, not a straight `'`.

## Key discovery 5: social icons are inline SVG, not a new icon-library dependency

Live uses Font Awesome webfont glyphs (`<i class="fab fa-instagram">`) — this project has no icon-font/icon-library dependency anywhere (checked `package.json`), and adding one solely for 2 icons would fail this project's dependency-vetting bar (a two-icon need doesn't justify a new dependency; simple inline SVG paths for the Instagram and Facebook glyphs are the standard-library-first choice). Live-measured per icon: circular button, border `~1px solid var(--color-ink)` (measured 0.8px in one query, 0px in another — inconsistent enough to treat as approximately 1px and confirm exact value during Task 4's live QA), `border-radius: 50%`, icon color `--color-ink`, ~51px button diameter (also measured inconsistently as 61.6px in one query — same "confirm during QA" note), `gap: 20px` between the two icons (this one measured consistently, matches `--space-xs`).

**Exact links (live-confirmed, no `rel` attribute on either — replicate exactly):**

| Icon      | Link                                          | `target`            |
| --------- | --------------------------------------------- | ------------------- |
| Instagram | `https://www.instagram.com/lawrence.skaters/` | `_blank` (no `rel`) |
| Facebook  | `https://www.facebook.com/SKATELSA`           | `_blank` (no `rel`) |

## Key discovery 6: `Footer.astro` mounts in `BaseLayout.astro`, not `index.astro`

Every prior section (`Hero`, `About`, `Parks`, `WhoWeAre`) is homepage content, rendered inside `index.astro`'s `<main>`. The footer is page chrome — shared across every page the site will ever have, exactly like `<Header />`, which is already rendered in `BaseLayout.astro` outside any page's `<main>`/`<slot>` content. `Footer.astro` follows the same pattern: rendered in `BaseLayout.astro` after `<slot />` (and before `<CursorDot />`), not added to `index.astro`. This is an intentional architecture choice (matching an existing precedent, not inventing one), not scope creep.

## Key discovery 7: copyright year — live is a hardcoded "© 2026", this build uses a computed year instead (flagged deviation)

Live HTML has the literal, non-templated text "© 2026" — it will silently go stale on every WordPress site of this kind once the calendar turns. Every other piece of copy on this site has been replicated character-for-character per this project's exact-replica policy, but a hardcoded year is a real, avoidable defect (not a design/content choice like Our Parks' empty `alt=""`), so this phase deliberately deviates: render `© {new Date().getFullYear()}  Lawrence Skaters Association` instead of a literal "2026". Flagged here per this project's practice of surfacing deviations rather than silently making them — reject/override this call during plan review if literal replication is preferred instead.

## Recommended approach

**Component structure:** single file, `src/components/Footer.astro` — three `<section>`s (support/donate, social icons, copyright) inside one `<footer>` element. No new sub-components: the two social icons are simple enough to inline as SVGs directly (matching `WhoWeAre.astro`'s single-file simplicity, avoiding a premature `SocialIcon.astro` abstraction for two static icons).
