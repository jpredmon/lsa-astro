# skatelawrence.com Migration — Phase 7: Who We Are Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the "Who We Are" section: a "Who we are" headline (identical pattern to About Us/Our Parks), followed by a short 3-paragraph text blurb ending in a contact email link. This is the last homepage content section before the footer/donate area (out of scope, future phase).

**Architecture:** `WhoWeAre.astro` — a single self-contained component, no sub-components and no images. Reuses the existing `AnimatedHeadline` (no changes needed) for the headline, and a plain `<p>`-based body block styled from existing typography tokens (`--font-size-body`/`--line-height-body`/`--color-ink`) — a different pattern from About Us's `<h5>` one-liners, since this content is genuinely body-copy-length text.

**Tech Stack:** Astro components, existing design tokens (no new global tokens needed for this component; two small live-measured values are kept local/scoped rather than promoted — see Key discovery 3).

## Global Constraints

- TypeScript strict mode, no implicit `any` (N/A here — no script logic, but any component code must still comply).
- No new functionality beyond what's specified; no analytics.
- Conventional commits, imperative present tense, no `Co-Authored-By: Claude` trailer.
- Every visual/behavioral detail confirmed via live `getComputedStyle`/DOM, not assumed from spec prose (the spec's own "short team blurb" description undersells this — see Key discoveries below).
- When trueing up spacing against live, measure the box model (padding/margin) on both sides, not just the visible gap between elements (see [[feedback-verify-against-live-computed-styles]]).
- Astro's compiler silently collapses a newline-adjacent whitespace text node to nothing, not to a single space (a real bug hit twice already in Phase 6 — see Key discovery 6). Any inline markup with text immediately before/after a tag must stay on one line or use an explicit `{' '}` — do not let Prettier or manual formatting introduce a newline at those boundaries.

## Context

Phases 1–6 (scaffold, tokens, header/nav, hero, about, parks) are complete and live at `lsa-astro.pages.dev`. This phase adds Who We Are, the section immediately following Our Parks and immediately preceding the footer (Support/Donate is a future phase, embedded in the live site's footer template, not this section).

**Research method:** live HTML via `curl` with a realistic UA, plus live Chrome `getComputedStyle`/DOM inspection against `https://skatelawrence.com`.

## Key discovery 1: Nav's "Contact" label actually points to the "Who We Are" section — a live mislabeling, replicated exactly

The live site's Nav has a "Contact" link (`href="#contact-id"`, already built in Phase 3 at `src/components/header/Nav.astro:12` — no changes needed there). That anchor ID is attached to the section whose headline reads "Who we are", not to any separate contact form or address block — live-confirmed via `document.getElementById('contact-id')`. This is the same category of live quirk as Phase 3's "no working mobile menu" finding: a mislabeled nav item on the production site, not a bug to fix. `WhoWeAre.astro`'s headline section keeps `id="contact-id"` so Nav's existing anchor continues to work unchanged.

## Key discovery 2: headline reuses the exact About Us/Our Parks pattern — no new tokens, no component changes

Live-measured on `#contact-id`: `margin: 110px 0 0` (matches `--space-section-gap`), `padding: 0 30px` (matches `--space-sm` side padding), widget-wrap `padding: 10px` (matches `--space-headline-section`). The `AnimatedHeadline` widget's own settings (`highlight_animation_duration: 1200`, `highlight_iteration_delay: 8000`, marker `underline`, loop `yes`) are identical to every other section headline already built — confirms `cycleDurationMs={8000}` and no further verification needed, per the same codepath already proven twice.

## Key discovery 3: body blurb is plain body-copy text, not an `<h5>` one-liner like About Us — reuses typography tokens directly, two small values kept local (not promoted)

Live-measured on the text-editor widget containing the 3 paragraphs: `font-size: 16px`, `line-height: 30px` (i.e. `1.875em` at 16px) — this **exactly matches the existing `--font-size-body`/`--line-height-body` tokens** already in `tokens.css` (unlike About Us's body sections, which use `<h5>` styling for short declarative one-liners, this content is multi-sentence body copy). Text is centered, color `--color-ink`.

Two live-measured values don't fit the `xs`/`sm`/`md`/`lg` spacing scale and, per this branch's own established convention (a value is only promoted to a shared token once it has a second consumer — see Phase 6's final-review finding on `--space-about-section-gap`), are kept as local, well-commented values scoped to this one component rather than new global tokens:
- **30px top/bottom padding** on the body block: live has two nested Elementor layers contributing to this (the text-editor widget's own 20px all-around padding, plus its `e-con-inner` parent's 10px top/bottom padding) — folded into one `30px` value, same fold-multi-layer-padding-into-one pattern already used for `--space-about-video-gap` and `--space-parks-grid-gap-top`.
- **16px margin-bottom between paragraphs**: live-measured `margin: 0 0 16px` on the first two `<p>` elements; the last paragraph has `margin: 0` (flush against the section's own bottom padding).

## Key discovery 4: contact email link styling differs from Our Parks/Hero — no highlight color, no `target="_blank"`

Live HTML: `<p>Contact us: <strong><a href="mailto:lawrenceskatersassociation@gmail.com">lawrenceskatersassociation@gmail.com</a></strong></p>` — decoded via the browser's rendered DOM (Cloudflare's email-obfuscation cipher decodes client-side; the raw HTML source only contains an encoded `data-cfemail` hex string, not usable directly). The link has **no `target`/`rel` attributes** (unlike the Our Parks photo-credit links, which are true external-site links with `target="_blank" rel="noopener"` — a `mailto:` link isn't "external" in that sense, and live doesn't treat it that way). Live-measured link color is `rgb(29, 28, 28)` (= `--color-ink`, i.e. **not** `--color-highlight-yellow` like Our Parks' credit links), `text-decoration: none`, `font-weight: 700` (from the `<strong>` wrapper — the anchor itself doesn't add its own weight or color, it inherits/is overridden to plain bold body text).

**Exact content (character-for-character, content-accuracy critical):**
```
<p>A revolving and evolving crew.</p>
<p>Assembled by JP Redmon.</p>
<p>Contact us: <strong><a href="mailto:lawrenceskatersassociation@gmail.com">lawrenceskatersassociation@gmail.com</a></strong></p>
```

## Key discovery 5: section is flush against the footer — 0px additional gap needed

Live-measured: the blurb's own outer container has `margin-bottom: 0` and `padding-bottom: 0` beyond what's already folded into the 30px body-block padding (Key discovery 3) — its bottom edge exactly touches the footer's top edge (`getBoundingClientRect()` delta = 0px). No trailing spacer or extra margin needed after the last paragraph.

## Key discovery 6: resolves a parked Phase 6 finding — `Parks.astro`'s grid-section bottom padding was measured wrong

Phase 6's final review flagged (and parked, non-blocking) that `.parks__grid-section`'s bottom padding (`var(--space-md)`, 50px) looked like a ~40px mismatch against live, bordering this not-yet-built section, and recommended whoever builds Who We Are re-derive the correct value. Live-measured now: the total gap between Our Parks' last image and Who We Are's headline section is **120px total**, decomposed via `getBoundingClientRect()` as **110px** (Who We Are's own `--space-section-gap` top margin — Key discovery 2) **+ 10px** (Our Parks' own grid container's trailing padding-bottom, confirmed on its live `e-con-inner` element). `Parks.astro` currently uses `var(--space-md)` (50px) for this — **wrong**, and this phase corrects it to a new `--space-parks-grid-gap-bottom: 10px` token (doesn't fit the `xs`/`sm`/`md`/`lg` scale, same as its sibling `--space-parks-grid-gap-top`). This is a small, live-data-justified fix to a previous phase's file — flagged explicitly here rather than silently bundled, since it's the direct reason this phase's own top-of-section spacing comes out correct.

## Recommended approach

**Component structure:** single file, `src/components/WhoWeAre.astro` — headline section (`id="contact-id"`, matching Nav's existing anchor) + a body section with 3 hardcoded paragraphs (this content isn't per-instance/repeated like Our Parks' 5 photos, so no slot/prop API is needed — plain static markup, same simplicity level as About Us's `<h5>` one-liners).
